# Research: develop's Partner Membership/RBAC vs. extending main's RBAC in place

Issue: [#148](https://github.com/3mrhussein/findeg/issues/148) (child of map [#146](https://github.com/3mrhussein/findeg/issues/146)).
Primary sources: `develop` branch (as of commit `501ee3b1`) via PR [#73](https://github.com/3mrhussein/findeg/pull/73) ("Manage scoped Partner Memberships and Workspace context", merged into `develop`, +7451/-50), issue [#56](https://github.com/3mrhussein/findeg/issues/56) ("Manage Partner Memberships and Workspace context"), issue [#50](https://github.com/3mrhussein/findeg/issues/50) (user stories 18–20), and `main`'s current `backend/src/features/identity` + `db/src/schema/identity`.

PR #73 had no reviewer comments (`gh pr view 73 --comments` returned empty) — its description and diff are the only PR-level source.

## 1. Schema shape

**main** (`db/src/schema/identity/identity-access.ts`):
- `organizations` (id, code, name, isActive) — a generic tenant/org table, already RBAC-adjacent.
- `roles` (id, code: `RoleId`, name) — fixed catalog of roles, no scoping baked into the row itself.
- `permissions` (id, code: `PermissionCode`, name).
- `role_permissions` (roleId, permissionId) — static role→permission mapping.
- `user_roles` (userId, roleId, scope: `RoleScope` = `'global' | 'organization'`, organizationId nullable) — this is the *only* scoping mechanism, unique on `(userId, roleId, scope, organizationId)` (`identity-access.ts:146-152`).
- `user_permissions` — per-user grant/revoke overrides.
- `organization_memberships` (organizationId, userId, status) — unique on `(organizationId, userId)` (`identity-access.ts:197-198`), but this table is **not** read anywhere in `getAuthorizationContext` (see below) — it looks like a stub that was never wired into authorization.

Authorization resolution (`db/src/queries/identity/users.ts:113-175`, `getAuthorizationContext`) flattens **all** of a user's role rows across **every** organization they hold a role in into one global `permissionCodes`/`activeRoleIds` array, and picks a single `scopedRole` via `roleRows.find(row => row.scope === 'organization' ...)` — i.e., the *first* org-scoped role found, not one selected per request. There is no concept of "the organization active for this request" anywhere in `backend/src/features/identity/application` (`buildCurrentSessionPayload.ts`, `AuthService.ts`, `CurrentSessionIdentityResolver.ts` all just pass through a single `organizationId`).

**develop** (`db/src/modules/partner-management/schema.ts`, migration `db/migrations/0003_partner_memberships.sql`):
- `business_partners` (id, code, nameEn, nameAr, status ∈ `{onboarding, active, suspended, closed}` via CHECK, `authorizationVersion`).
- `partner_invitations` (id, businessPartnerId, email, `roles: text[]`, `tokenDigest` unique, inviterId, expiresAt, status ∈ `{pending, accepted, revoked}`, createdAt) with a CHECK constraining `roles` to the fixed additive set `{partner-administrator, list-manager, collection-staff, report-viewer}`, and a **partial unique index** `one_pending_partner_invitation on (business_partner_id, email) where status = 'pending'` (schema.ts:59-61 / migration line "CREATE UNIQUE INDEX ... WHERE ... = 'pending'").
- `partner_memberships` (id, businessPartnerId, userId, invitationId **unique** FK, `roles: text[]`, status ∈ `{active, suspended, ended}`, `authorizationVersion`, createdAt), with a **partial unique index** `one_current_partner_membership on (business_partner_id, user_id) where status <> 'ended'` (schema.ts:90-92).
- `partner_access_history` — append-only audit trail (actorId, action, before/after jsonb).

Notably develop's own schema file re-exports `organizations`/`organizationMemberships` from main's exact identity-access schema with the comment *"Owner-scoped schema construction surface. Legacy mappings are retained until replacement."* (`db/src/modules/partner-management/schema.ts:1-2`) — i.e., develop did **not** reuse `organizations`/`organizationMemberships` for Business Partner/Membership; it built four new tables from scratch and kept the old org tables only for backward compatibility during migration.

**Gap to reach parity on main**: main's `roles`/`permissions`/`role_permissions`/`user_roles` model has no per-row concept of a fixed *additive* role set scoped to a specific external entity with lifecycle (`active/suspended/ended`), no invitation/token table, and no audit-history table. Reaching what develop has would mean adding **4 new tables**, not new columns on the existing RBAC tables — `roles`/`permissions` are shape-wise wrong for this (they model a small fixed global catalog checked against a flat per-user set, not a `roles: text[]` column scoped per business-partner-membership row with idempotent invite/accept semantics).

## 2. Invitation → acceptance flow

develop's flow (`backend/src/modules/partner-management/public.ts:255-321`, persistence in `infrastructure/persistence.ts:86-190`):

1. **`invite`** (`public.ts:255-293`): validates the caller can manage that partner (`manage()`, `public.ts:111-126`), validates email/roles, generates a random token (`security.newToken()`), stores only its digest (`security.digest(token)`), and calls `store.issueInvitation` which, in one statement, revokes any existing *pending* invitation for that `(businessPartnerId, email)` pair and inserts the new one (`persistence.ts:86-103`) — replacing rather than erroring on resend.
2. **`acceptInvitation`** (`public.ts:294-321`): looks up the invitation by token digest, checks it is `pending`, unexpired, and that the accepting session's *verified* email matches the invitation email exactly; **locks the parent Business Partner row** (`store.lockPartner`, a `SELECT ... FOR UPDATE`, `persistence.ts:47-54`) before checking partner status; checks the user doesn't already have a non-`ended` membership for that partner (`membership-exists` short-circuit); then calls `store.acceptInvitation`, which inserts the `partner_memberships` row and flips the invitation to `accepted` (`persistence.ts:123-138`) — both writes happen inside the caller's transaction (the whole `PartnerStore` is bound to one `TransactionDatabase`, see `createPartnerOperations` in `backend/src/application/partner-operations.ts:19`, which the runtime wraps in a single DB transaction per request/operation).
3. An audit row is written to `partner_access_history` in the same transaction.

**main has no analogous pattern.** There is no invitation/token table or accept-flow anywhere under `backend/src/features/identity`; the closest thing is plain role assignment (`user_roles` insert) done directly by an admin, with no invite/accept step, no token, no expiry. This would be **wholly new** on main, not an extension of an existing pattern.

## 3. Final-administrator protection & membership lifecycle

Enforced entirely at the **application-service level**, inside the same DB transaction, using data fetched under the partner row lock:

- `updateMembership` (`public.ts:153-196`): computes `removesAdministrator` (the target membership is currently active+admin, and the new state either isn't active or drops the admin role) and, if true, requeries all memberships for that partner and checks whether **any other** active membership still has `partner-administrator`; if not, returns `{status: 'last-administrator'}` without writing (`public.ts:172-186`).
- `changePartnerStatus` (`public.ts:226-254`): reactivating a partner (`status: 'active'`) requires at least one active administrator membership to exist, else `{status: 'last-administrator'}` (`public.ts:238-244`).
- Both checks run after `store.lockPartner(partnerId)` (`SELECT ... FOR UPDATE`), so a concurrent request against the same Business Partner is serialized rather than racing on the membership count.
- Membership lifecycle states (`active/suspended/ended`) and "no changes once ended, or once partner closed" (`public.ts:170-171`) are plain in-code state-machine checks, not DB triggers or CHECK constraints — the DB only constrains membership `status` to be one of the three values and enforces "at most one non-ended membership per (partner,user)" via the partial unique index.
- Resend/expiry: resend is "revoke-then-reissue" inside `issueInvitation` (§2); expiry is a plain `expiresAt` timestamp compared against `security.now()` at accept-time (`public.ts:301`) — no scheduled job, no DB-level TTL.

**Fit with main's RBAC**: main's `PermissionService`/`hasPermission`/`hasRole` (`backend/src/features/identity/application/services/PermissionService.ts:16-40`) is a pure *lookup* — "does this flat permission/role set contain X" — sourced from `getAuthorizationContext`, which has no concept of counting active holders of a role scoped to one external entity, and no row-locking step before a role-mutation (no equivalent of `lockPartner`). Final-admin protection is a **stateful, transactional, cross-row invariant check** ("is this the last active admin *for this specific partner*") that has no counterpart in main's current authorization code path at all — it isn't a permission check, it's a business-rule guard around a mutation, and would have to be added as new service logic regardless of which schema it sits on.

## 4. Concurrent-replay safety

Mechanism, concretely:
- `partnerInvitations.tokenDigest` is `unique` (`schema.ts:45`) — two invitations can never collide on token.
- Partial unique index `one_pending_partner_invitation on (business_partner_id, email) where status='pending'` guarantees at most one *live* invitation per partner+email at the DB level even under concurrent `invite()` calls (the earlier revoke-then-insert in `issueInvitation` is itself inside the caller's transaction, so a genuinely concurrent second `invite()` would serialize on this index or the partner row lock).
- Partial unique index `one_current_partner_membership on (business_partner_id, user_id) where status <> 'ended'` is the actual duplicate-acceptance guard: even if two `acceptInvitation` calls raced for the same invitation, the `lockPartner` `SELECT ... FOR UPDATE` on `businessPartnerId` (`persistence.ts:104-121`, comment: *"Serialize acceptance with issuance and membership changes on the Business Partner"*) forces them to execute the read-then-insert sequence one at a time; the second request's `membership-exists` check would already see the first request's freshly-inserted (and committed-within-tx-visible) row, or, failing that, the partial unique index would reject the duplicate insert outright.
- No `ON CONFLICT` upsert is used for the membership insert itself — the safety comes from the row lock + pre-check + unique index combination, not from `onConflictDoNothing`. (`onConflictDoNothing` *is* used for `createPartner`, `persistence.ts:40-45`, a different, simpler idempotency case.)

**Portability to main**: fully portable. Confirmed main uses the identical stack — `drizzle-orm/pg-core` Postgres, `db.transaction()` (used throughout `db/src/queries/**`, e.g. `db/src/queries/identity/create-admin-user.ts:13`), and `.for('update')` row locking already in production code (`db/src/queries/catalog/inventory.ts:148`, used for stock-reservation concurrency). Partial unique indexes with a `where` predicate are standard Drizzle/Postgres and require no new tooling. There is no technical obstacle to reusing this exact mechanism on main.

## 5. Bottom-line recommendation

**Layering a `PartnerMembership` concept on top of main's existing `identity` RBAC tables (`RoleId`/`RoleScope`/`PermissionCode`) is not straightforward, and develop's implementation shows why: partner access is a *different scoping and evaluation model*, not a variant of the same one.**

Strongest evidence:

1. **main's authorization context is flattened and computed once per session, not resolved per active entity.** `getAuthorizationContext` (`db/src/queries/identity/users.ts:113-175`) merges every `user_roles` row the user has — across *all* organizations — into one `permissionCodes`/`activeRoleIds` array, and derives a single `scopedRole` by taking the first `organization`-scoped row found, with no notion of "which organization is active for this request." develop's model is the opposite: `workspace()` (`backend/src/modules/partner-management/public.ts:81-110`) resolves a `CurrentSession` extension (`session.partner.{businessPartnerId, membershipId, roles, authorizationVersion}`) scoped to exactly one selected Business Partner per request, and every subsequent permission check (`manage()`, `public.ts:111-126`) re-derives that scope fresh. Bolting this onto main's tables would require redesigning `getAuthorizationContext` itself (adding request-scoped active-org selection) before a single `PartnerMembership` row could even be evaluated correctly — this is a structural change to identity's core session-resolution path, not an additive table.
2. **The final-administrator and replay-safety guarantees are cross-row, transactional invariants enforced with a row lock plus partial unique indexes scoped to the external entity** (`one_current_partner_membership`, `one_pending_partner_invitation`, both `WHERE`-filtered on `business_partner_id`, `db/migrations/0003_partner_memberships.sql`), evaluated inside a `SELECT ... FOR UPDATE`-locked transaction (`persistence.ts:47-54`, `104-121`). main's RBAC tables (`role_permissions`, `user_roles`) have no equivalent locking discipline or per-entity partial-uniqueness today, and `PermissionService` (`backend/src/features/identity/application/services/PermissionService.ts`) is a stateless read path with no transactional-mutation guard at all. This is a distinct service/enforcement layer, not an extension of permission-check code.

Recommendation: give Partner Workspace/Membership its **own module and its own tables** (as develop did — `business_partners`, `partner_invitations`, `partner_memberships`, `partner_access_history`), reusing main's `identity` feature only for what it already does well (verified-email `User`, session authentication) rather than trying to fit partner-scoped, lifecycle-bearing, invite/accept membership semantics into `RoleId`/`RoleScope`/`PermissionCode`. The mechanics developed (transaction + row lock + partial unique indexes) are directly portable to main's stack, so the *implementation techniques* should be reused even though the *schema and evaluation path* should not be forced onto identity's existing RBAC tables. main's dormant `organizations`/`organization_memberships` tables are the closest analog to Business Partner/Membership, but develop itself declined to build on them (`db/src/modules/partner-management/schema.ts:1-2`, explicitly kept only "until replacement"), which corroborates that they weren't fit for this purpose either.
