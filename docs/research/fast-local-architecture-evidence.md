# Fast local development: architecture source check

Checked 2026-10-24 for [Investigate architecture alternatives for fast local development](https://github.com/3mrhussein/findeg/issues/525). This supplements the [earlier persistence comparison](https://github.com/3mrhussein/findeg/blob/4fd0b10de83af8d8ed61f999e17921f85454a36e/docs/research/fast-local-persistence-options.md); it selects no architecture and runs no candidate.

## Shared SQL host

**Documented:** PGlite Socket accepts PostgreSQL clients, including postgres.js; it can own a filesystem-backed database and supervise a child command. Multiple clients multiplex one underlying connection, and SSL is unsupported. Its documentation explicitly warns that this differs from normal PostgreSQL. [Socket documentation](https://pglite.dev/docs/pglite-socket), [Node filesystem](https://pglite.dev/docs/filesystems).

**Published implementation:** Registry versions remain PGlite `0.5.11` and Socket `0.2.14`. Socket's published `package/src/index.ts` serializes protocol work and, while a transaction is open, selects work from its owning handler. Detaching that handler clears its queued work and calls `clearTransactionIfNeeded`, which rolls back the transaction and resumes the queue. The implementation therefore contains disconnect recovery; FindEg behavior remains unverified. It also explicitly ignores PostgreSQL `CancelRequest`. The server defaults to one accepted connection, requiring an explicit limit for two apps and their pools. [PGlite manifest](https://registry.npmjs.org/@electric-sql/pglite/0.5.11), [Socket manifest](https://registry.npmjs.org/@electric-sql/pglite-socket/0.2.14), [immutable published source archive](https://registry.npmjs.org/@electric-sql/pglite-socket/-/pglite-socket-0.2.14.tgz). The archive's file was byte-compared with this [pinned readable source](https://github.com/electric-sql/pglite/blob/e752dbe0a550ee74e5e175ae799e556758201682/packages/pglite-socket/src/index.ts#L72) and matched.

**Inference for FindEg:** A supervised shared SQL host preserves the existing postgres-js/Drizzle driver family and query implementations. It concentrates lifecycle changes in development composition, with fewer reasons to alter business packages. This is a hypothesis about change cost, not proof of compatibility, resource savings, session isolation or production concurrency. [Current connection](https://github.com/3mrhussein/findeg/blob/a4574376f34ad362487f89d2789b0504dbb9b9f4/db/src/connection.ts).

## Direct embedded driver and a shared owner

**Documented:** Drizzle can wrap a PGlite instance through `drizzle-orm/pglite`; this is a different driver import from FindEg's `drizzle-orm/postgres-js`. PGlite documents a browser worker proxy for multiple tabs sharing one instance; that does not establish Node process sharing. [Drizzle guide](https://orm.drizzle.team/docs/connect-pglite), [PGlite ORM support](https://pglite.dev/docs/orm-support), [browser worker](https://pglite.dev/docs/multi-tab-worker).

**Inference:** Two independent Next app processes still need one database owner and transport. Keeping the SQL protocol returns to the shared-host design. A custom query/transaction RPC adapter would create a new protocol; moving whole canonical business operations into a shared runtime would instead add an application transport, error/authorization mapping and lifecycle work. Neither follows automatically from direct-driver support. Independently opening the same data directory from both apps is not established as safe by these docs. Driver-specific database/transaction types and raw result behavior also need reconciliation. [FindEg transaction type](https://github.com/3mrhussein/findeg/blob/a4574376f34ad362487f89d2789b0504dbb9b9f4/db/src/queries/db-transaction.ts), [architecture ownership](https://github.com/3mrhussein/findeg/blob/a4574376f34ad362487f89d2789b0504dbb9b9f4/docs/adr/0020-domain-single-source-and-bounded-context-packages.md).

## Fakes and emulation

pg-mem still documents JavaScript-number numeric semantics and no timezone support; its FAQ says native PL/pgSQL is absent and extensions must be mocked. That is a concrete mismatch with FindEg's exact monetary persistence, Cairo-time reports and PL/pgSQL integrity triggers, regardless of client connectivity. It is not a transparent substitute for the agreed workflow target. [Limitations](https://github.com/oguimbal/pg-mem#-current-limitations), [FAQ](https://github.com/oguimbal/pg-mem/wiki/FAQ), [Order integrity migration](https://github.com/3mrhussein/findeg/blob/a4574376f34ad362487f89d2789b0504dbb9b9f4/db/migrations/0010_order_acceptance_and_reference.sql).

Context-owned persistence adapters are a viable design direction to investigate if portability itself is desired. A durable fake would still need shared ownership, atomic cross-context commits, constraint/error behavior and query semantics while invoking canonical Domain rules. Existing Drizzle-shaped injection is not such an adapter. Those responsibilities must be designed and tested explicitly rather than represented as successful canned responses. [Orders dependency type](https://github.com/3mrhussein/findeg/blob/a4574376f34ad362487f89d2789b0504dbb9b9f4/packages/orders/src/types.ts), [Order Acceptance guarantees](https://github.com/3mrhussein/findeg/blob/a4574376f34ad362487f89d2789b0504dbb9b9f4/docs/adr/0005-atomic-cod-order-acceptance.md).

## Conditional recommendation and next evidence

If the human prioritizes removing setup overhead with limited production change, evaluate the shared SQL host first. If storage portability is an independent goal worth a larger refactor, first design a concrete context-owned persistence interface and its cross-context transaction contract. Neither option is selected here.

A shared-host experiment must prove the full migration/seed chain, exact values/errors/triggers, both apps' real workflows, committed-data restart durability, cache freshness, transaction-owner disconnect recovery and cancellation/failure behavior. Compare whole-stack startup and resource use on the same dataset; source claims establish no measured savings. Preserve real-PostgreSQL integration/concurrency verification. No candidate installation, compatibility run, application test or benchmark was performed in this source check.

## Repository responsibilities and alternatives

Inspected baseline: `a4574376f34ad362487f89d2789b0504dbb9b9f4`.

The reusable persistence seam is PostgreSQL through postgres-js/Drizzle. Orders, Business Partners and School Supply Lists accept driver-shaped database objects; Catalogue, Identity, Inventory, checkout and Guest Order Access still include default-connected paths. Checkout does not obtain its database from `createOrders({ db })`. [Orders construction](https://github.com/3mrhussein/findeg/blob/a4574376f34ad362487f89d2789b0504dbb9b9f4/packages/orders/src/helpers.ts#L7), [checkout loading](https://github.com/3mrhussein/findeg/blob/a4574376f34ad362487f89d2789b0504dbb9b9f4/packages/orders/src/features/order-acceptance/helpers.ts#L86), [Catalogue construction](https://github.com/3mrhussein/findeg/blob/a4574376f34ad362487f89d2789b0504dbb9b9f4/packages/catalog/src/features/catalog-factory/index.ts#L13).

Commands own transactions. Order Acceptance shares one transaction across idempotency, authoritative re-quote, stock, frozen Order snapshots and Outbox writes. Order Status changes also commit stock effects, Outbox and audit atomically. A new persistence adapter must preserve those transaction scopes rather than make each repository independently atomic. [Acceptance](https://github.com/3mrhussein/findeg/blob/a4574376f34ad362487f89d2789b0504dbb9b9f4/packages/orders/src/features/order-acceptance/helpers.ts#L331), [status changes](https://github.com/3mrhussein/findeg/blob/a4574376f34ad362487f89d2789b0504dbb9b9f4/packages/orders/src/features/order-status-changes/helpers.ts#L30), [transaction joining](https://github.com/3mrhussein/findeg/blob/a4574376f34ad362487f89d2789b0504dbb9b9f4/db/src/queries/transaction.ts#L18).

Persistence behavior also includes frozen-snapshot triggers, stock checks, unique published Slots, last-administrator serialization, append-only audit, nested savepoints and SQLSTATE plus constraint-name mapping. Retaining Domain functions alone does not preserve these backstops. [Stock constraints](https://github.com/3mrhussein/findeg/blob/a4574376f34ad362487f89d2789b0504dbb9b9f4/db/migrations/0009_stock_reservations.sql#L24), [School Supply List constraints](https://github.com/3mrhussein/findeg/blob/a4574376f34ad362487f89d2789b0504dbb9b9f4/db/migrations/0006_school_supply_list_lifecycle.sql#L45), [Business Partner locking](https://github.com/3mrhussein/findeg/blob/a4574376f34ad362487f89d2789b0504dbb9b9f4/db/src/queries/partners/index.ts#L81), [Order Reference errors and savepoints](https://github.com/3mrhussein/findeg/blob/a4574376f34ad362487f89d2789b0504dbb9b9f4/db/src/queries/sales/orders.ts#L288).

| Direction | Setup, fidelity and maintenance | Change cost and production exposure |
| --- | --- | --- |
| Current driver with one supervised durable SQL host | Shares state and reuses actual queries, migrations and operations. Pool/protocol compatibility and serial-engine usefulness require proof. | Smallest expected application change; most work can stay in local composition. This is an assessment, not a measured cost. |
| Direct embedded driver with an explicit shared owner | Retains SQL and may avoid the socket adapter, but needs a transport between the owner and both apps. | Driver-specific executors/results plus a new query protocol, or broader application RPC. No existing generic executor makes this a one-import swap. |
| Context-owned persistence adapters | Makes alternative storage explicit and could improve isolated tests. Requires real durable sharing, transaction coordination and invariant enforcement. | Broad context/query migration and contract tests for both adapters; justified if portability is independently valuable or a narrow SQL substitution fails. |
| Shared process running canonical operations | Centralizes storage ownership and delivery composition. Both apps call the same operations remotely. | Adds transport, trusted identity propagation, authorization, error and Money serialization, availability and app integration work. Viable, but larger than the current setup objective alone justifies. |

Whole-operation canned mocks conflict with the agreed fidelity contract. A lower persistence fake is possible only with deliberate interfaces and the semantics above; it is not an available runtime switch. ADR-0020 keeps Domain canonical, commands responsible for transactions, Backend responsible for infrastructure/composition and contexts independent of Backend. [Agreed workflow fidelity](https://github.com/3mrhussein/findeg/issues/521#issuecomment-6389145902), [ADR-0020](https://github.com/3mrhussein/findeg/blob/a4574376f34ad362487f89d2789b0504dbb9b9f4/docs/adr/0020-domain-single-source-and-bounded-context-packages.md).

## Bounded changes to consider after the human decision

These are proposals for the selected experiment and eventual plan, not completed refactors:

1. A local lifecycle module owning start/readiness/stop, app child processes, host ownership and failure cleanup. Resolve paths, state identity, ports and environment before importing default-connected modules. Root development currently starts Docker; environment loading and pool construction happen at import time. [Root commands](https://github.com/3mrhussein/findeg/blob/a4574376f34ad362487f89d2789b0504dbb9b9f4/package.json#L9), [environment loading](https://github.com/3mrhussein/findeg/blob/a4574376f34ad362487f89d2789b0504dbb9b9f4/configs/env/src/core.ts#L14), [connection construction](https://github.com/3mrhussein/findeg/blob/a4574376f34ad362487f89d2789b0504dbb9b9f4/db/src/connection.ts#L14).
2. Reuse the existing `EmailProvider` seam, selecting local capture consistently for response-triggered drains and scheduled sweeps. Preserve real Outbox retries and secret generation. Current default wrappers create Resend; capture composition must reach both wrappers. [Outbox factory](https://github.com/3mrhussein/findeg/blob/a4574376f34ad362487f89d2789b0504dbb9b9f4/backend/src/features/outbox/application/factory.ts#L17).
3. An app-layer cache policy or invalidation interface that proves Dashboard edits appear after a normal Storefront refresh. Storefront caches Catalogue reads for hours; Dashboard updates its own process tags. A shared database does not prove visibility. [Cached reads](https://github.com/3mrhussein/findeg/blob/a4574376f34ad362487f89d2789b0504dbb9b9f4/frontend/storefront/src/data/catalog/queries.ts#L46), [Dashboard writes](https://github.com/3mrhussein/findeg/blob/a4574376f34ad362487f89d2789b0504dbb9b9f4/frontend/dashboard/src/data/products/actions.ts#L30). Consult the installed Next.js documentation before selecting the implementation.
4. Explicit bootstrap paths/executors and reliable cleanup only where the experiment needs them. Current `db:setup` uses generate/push/seed; compatibility requires init plus the complete historical migration chain, as the real integration harness already does. Separate connection construction from environment loading only if necessary; do not first inject every context. [Database commands](https://github.com/3mrhussein/findeg/blob/a4574376f34ad362487f89d2789b0504dbb9b9f4/db/package.json#L27), [migration harness](https://github.com/3mrhussein/findeg/blob/a4574376f34ad362487f89d2789b0504dbb9b9f4/configs/vitest/postgres/global-setup.ts#L29).

## Proposed proving sequence and test ownership

If the human chooses the current SQL seam, reframe the provisional experiment around three ordered gates:

1. **Storage contract:** pinned candidate; empty-state init, every migration, seeds and reset; exact Money/date/JSONB/array results; error metadata, triggers, savepoints, rollback, two-client transaction ownership, disconnect recovery and cancellation behavior. Stop at the first material incompatibility and report it precisely.
2. **Application contract:** both actual apps; login and denied permissions; Catalogue/profile edits and next-refresh visibility; Quote/reconfirmation, Order Acceptance, idempotent replay and stock rollback; Order Status stock effects; School Supply List lifecycle and checkout; Business Partner membership, invitations and reports; real local Outbox capture/failure/retry. Restart either app and then the host, verifying committed edits survive. Demonstrate implemented workflows through canonical operations.
3. **Usefulness:** compare equivalent data and journeys on the same machine, recording commands, cold/warm readiness, first-request/restart latency, whole-process-tree memory and idle/workload CPU. Include the helper and both apps; state Docker baseline attribution. Usability thresholds belong to the later human-evaluated experiment; no speed or memory improvement is established now.

Stop and return to the architecture decision if the candidate needs weaker integrity, skipped implemented workflows, duplicate business rules, leaked transaction ownership or an unbounded production rewrite. A targeted socket fix or direct-driver/shared-owner design may then be investigated; neither is silently authorized by this recommendation.

Domain keeps pure-rule tests; contexts keep business integration tests; Backend keeps delivery/composition tests. A candidate-specific harness covers compatible storage/workflow cases and process restart/failure behavior. Keep the existing real-PostgreSQL harness and contention suites: they deliberately use distinct backend processes and `pg_blocking_pids`, which a serial engine cannot validate. [Concurrency helpers](https://github.com/3mrhussein/findeg/blob/a4574376f34ad362487f89d2789b0504dbb9b9f4/configs/vitest/postgres/index.ts#L38).

Human direction and experiment selection remain pending. The provisional prototype and map dependencies have not been changed. This note is evidence for that decision, not its resolution.
